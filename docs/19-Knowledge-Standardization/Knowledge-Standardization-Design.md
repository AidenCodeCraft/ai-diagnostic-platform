# 知识库收录规范化设计清单

> 归属：AI Diagnostic Platform · 知识库标准化
> 目标：让知识条目「结构统一、可审查、可被 AI 精确定位」；human 自由填写不可靠，因此采用「前端一键格式化 + 分屏提交后预览 + 后端强制规范化」三层保障。
> 状态：设计评审中（未开始编码）

---

## 1. 背景与目标

### 1.1 现状问题

1. `KnowledgeDocument.content` 是自由 Markdown，格式不可控（标题层级混乱、章节缺失、日志特征散落）。
2. 「文档内容」与「诊断剧本（KnowledgeDiagnosisProfile）」双轨维护，容易漂移。
3. AI 定位依赖标题文本（`_extract_markdown_section` / 图片 `anchor`），内容不规范时锚点丢失、定位不稳定。

### 1.2 目标

- 知识条目有**标准模板**，人可读、机可解析。
- 入库前**自动规范化 + 校验**，质量可量化、可审查。
- AI 能定位到「文档 → 章节 → 行号」，回答可引用具体位置。
- **模板解析自动生成诊断剧本**，手填仅作覆盖/补充。

## 3. 总体原则（三层保障）

```
前端「一键格式化」    → 减少人工劳动（可被忽略）
前端「提交后预览」    → 让用户看到保存后的样子（可被忽略）
后端「强制规范化」    → 入库时统一 Normalizer + Validator（最终兜底，防绕过）
```

- 前端"格式化预览"与后端"入库规范化"**共用同一套逻辑**（通过 `format/preview` 接口），保证所见即所得。

## 4. 数据模型

### 4.1 doc_type 分类调整

| doc_type | 对应内容 | 模板 | 校验强度 | 生成诊断剧本 |
| --- | --- | --- | --- | --- |
| `case` | 现场问题处理示例 | 强制模板 | 完整校验 | 是（日志定位用） |
| `faq` | FAQ | 问答模板 | 基础校验 | 否 |
| `code_logic` | 代码逻辑说明 | 代码模板 | 基础校验 | 否 |
| `knowledge` | 基础知识 | 知识模板 | 基础校验 | 否 |
| `folder` | 文件夹 | — | — | — |

> 说明：四类内容**都能参与日志定位**——只要有「日志特征/关键字」，其关键词/正则可参与日志检索；`case` 要求最强，FAQ 通过「关键字/关键字解释」参与，代码逻辑/基础知识是自由文档、可选日志特征。

### 4.2 模板与必填字段

#### 4.2.1 现场问题处理示例（`case`）

按真实内容（现象 / 原因 / 处理结果）定模板，并保留特征点与日志特征用于定位：

```markdown
# <标题>
## 现象
## 特征点（建议：城市/设备类型/版本等，key: value 行）
## 原因
## 处理结果
## 日志特征（建议必填，用于日志定位）
### 关键词
- ...
### 正则
- ...
### 排除正则
- ...
## 关联知识（可选：FAQ / 代码逻辑 / 基础知识）
## 相关图片（可选）
```

| 字段 | 必填级别 |
| --- | --- |
| 标题 | **必填** |
| 现象 | **必填** |
| 原因 | **必填** |
| 处理结果 | **必填** |
| 特征点（城市/设备/版本） | 建议（缺失只提示） |
| 日志特征（关键词或正则 ≥1） | 建议（缺失只提示，且该条目不参与日志定位） |
| 关联知识 / 相关图片 | 可选 |

> 特征点示例：`城市: 潜江`、`设备类型: D3C`、`版本: V2.1`。Normalizer 解析为 `features` JSON，供检索时按设备/城市过滤匹配。
> 未填日志特征时，Normalizer 可从「现象/原因」自动抽取候选关键词（数字、错误码、引号内术语），标记为「自动候选」待人工确认。

#### 4.2.2 FAQ（`faq`）

按现有 FAQ 规定格式：

```markdown
# 标题
## 现象
## 分析
## 关键字
## 关键字解释
## 示例（可选）
## 作者（可选）
```

| 字段 | 必填级别 |
| --- | --- |
| 标题 | **必填** |
| 现象 | **必填** |
| 分析 | **必填** |
| 关键字 | **必填** |
| 关键字解释 | **必填** |
| 示例 / 作者 | 可选 |

FAQ 的「关键字」进入 `log_keywords`，**参与日志定位**（不是纯参考知识）。

#### 4.2.3 代码逻辑（`code_logic`）

面向某块业务写的文本说明，**无固定格式、不要求代码位置**：

```markdown
# 标题
<正文（自由文档，说明业务逻辑/流程/注意事项）>
```

| 字段 | 必填级别 |
| --- | --- |
| 标题 | **必填** |
| 正文 | **必填** |
| 日志特征（可选；绝大多数不含） | 可选 |
| 关联知识 | 可选 |

校验仅做基础项：标题/正文非空、重复检测。

> 代码逻辑**一般不参与日志定位**，主要作为「判断用户提问的依据」——校验用户描述是否符合业务逻辑、纠正低级误区（详见 4.7）。

#### 4.2.4 基础知识（`knowledge`）

业务或设备的常规说明、声明，**无固定格式**：

```markdown
# 标题
<正文（自由文档）>
```

| 字段 | 必填级别 |
| --- | --- |
| 标题 | **必填** |
| 正文 | **必填** |
| 日志特征（可选；绝大多数不含） | 可选 |
| 关联知识 | 可选 |

校验仅做基础项：标题/正文非空、重复检测。

> 基础知识**一般不参与日志定位**，主要作为「判断用户提问的依据」（业务/设备常识），用于校验用户前提、纠正误区（详见 4.7）。

#### 4.2.5 必填字段汇总

| 类型 | 必填（hard，缺则不能 active） | 建议（warn） | 日志定位 | 主要用途 |
| --- | --- | --- | --- | --- |
| `case` | 现象、原因、处理结果 | 特征点、日志特征 | 通过日志特征 | 诊断证据 |
| `faq` | 现象、分析、关键字、关键字解释 | 示例、作者 | 通过关键字 | 参考 + 日志定位 |
| `code_logic` | 正文（标题必填） | 日志特征、关联知识 | 一般不参与 | 判断提问依据 / 纠正误区 |
| `knowledge` | 正文（标题必填） | 日志特征、关联知识 | 一般不参与 | 判断提问依据 / 常识校验 |

### 4.3 分节模型 `KnowledgeSection`（新增表，文档 1:N）

| 字段 | 说明 |
| --- | --- |
| `id` | PK |
| `doc_id` | FK `knowledge_documents.id` |
| `section_key` | 模板章节键（如 `log_signature`） |
| `title` / `level` | 章节标题/层级 |
| `start_line` / `end_line` | 在规范化后内容中的行号范围 |
| `content` | 章节正文 |
| `position` | 顺序 |

### 4.4 文档元信息 `KnowledgeDocumentMeta`（新增表，1:1）

| 字段 | 说明 |
| --- | --- |
| `doc_id` | FK unique |
| `quality_score` | 0–100 质量分 |
| `content_hash` | 规范化后内容哈希（去重/版本） |
| `template_key` | 使用的模板（case/faq/code_logic/knowledge） |
| `normalized_at` | 最近规范化时间 |

> 采用新表而非给 `knowledge_documents` 加列，避免运行时 `create_all` 无法 ALTER 既有表的问题；与既有的 `knowledge_images`、`knowledge_diagnosis_profiles` 保持一致。

### 4.5 诊断剧本生成规则（模板 → profile）

各类型按模板解析生成 profile（缺失字段可由用户「进阶覆盖」）：

| 类型 | symptom | log_keywords | root_cause | solution | 其他 |
| --- | --- | --- | --- | --- | --- |
| `case` | 现象 | 「日志特征 › 关键词」 | 原因 | 处理结果 | environment=特征点；features=城市/设备/版本 |
| `faq` | 现象 | 关键字 | 分析 | 分析（或空） | 关键字解释保留在正文，可展示 |
| `code_logic` | 可选（正文首段） | 「日志特征 › 关键词」（若有） | — | — | — |
| `knowledge` | 可选（正文首段） | 「日志特征 › 关键词」（若有） | — | — | — |

- 自动生成时 `source = "template"`；手填覆盖 `source = "manual_override"`；自进化候选 `source = "ai_candidate"`、`status = "draft"`。
- `case` 必生成剧本；`faq` 生成精简剧本；`code_logic` / `knowledge` 仅在含日志特征时生成日志字典部分。

### 4.6 参考知识 vs 诊断证据

- **日志证据来源**：四类内容都可提供日志证据——`case` 的日志特征、FAQ 的关键字、代码逻辑/基础知识可选的日志特征；命中即进入证据链。
- **诊断结论**：必须有日志证据（来自任一类型的命中）；无证据不得输出诊断结论（阶段 B 强约束不变）。
- **参考性回答**：无日志证据时，FAQ/代码逻辑/基础知识命中可给出回答，但标注「来自知识库、未在日志中验证」；`case` 无日志特征则只作经验参考，不产出结论。
- **关联知识**：`case` 可通过「关联知识」引用 FAQ/代码逻辑/基础知识，检索时一并展开（已确认实现）。

### 4.7 提问依据与误区纠正（补充设计）

用户会犯一些低级错误（误解业务逻辑、记错设备行为等）。代码逻辑/基础知识正是用来**判断用户提问是否成立**的依据，而不是日志定位材料。

- **检索阶段**：`case` 的日志特征、FAQ 的关键字用于日志定位；`code_logic` / `knowledge` 命中用于理解问题前提与业务逻辑。
- **回答阶段**：若用户描述与 `code_logic` / `knowledge` 冲突，AI 应先指出「按文档逻辑，实际应为 …」，引用对应文档，再继续回答；不要顺着错误前提硬答。
- **引用格式**：`《文档标题 · 章节 · 第 L1–L9 行》`。
- **与强约束的关系**：误区纠正属于「基于知识库的判断」，不需要日志证据；但若要下诊断结论，仍必须有日志证据。

## 5. Normalizer（规范化）

### 5.1 规则（确定性、幂等）

- 标题层级归一：只保留一个 H1（文档标题），章节统一为 H2，子节为 H3。
- 章节识别与重排：按模板顺序重排已知章节；未知章节保留在末尾。
- 空白/格式清理：连续空行合并、行尾空白、表格闭合、代码块语言标注。
- 日志特征抽取：从「日志特征」子结构解析出关键词/正则/排除正则。
- 生成 `section_key` 与分节行号范围。
- 幂等：同一内容多次规范化结果一致。

### 5.2 LLM 兜底

- 仅当规则无法识别章节结构（如整篇无标题的纯文本）时启用。
- 产物为「模板草稿」：插入标准章节骨架、标注需人工补充处；`status = draft`，进入审核。

## 6. Validator（校验与质量分）

### 6.1 校验项分级

| 级别 | 校验项 | 处理 |
| --- | --- | --- |
| error | 缺必填章节 | 禁止 active，只能 draft |
| error | 必填章节为空 | 同上 |
| error | 正则无法编译 | 同上 |
| error | 标题与已有条目重复/高度相似 | 同上 |
| warn | 信息量不足（章节过短） | 允许 draft，提示完善 |
| warn | 日志特征为空（case） | 允许 draft，提示补全 |
| warn | 图片引用不存在 | 允许 draft，提示修复 |

### 6.2 质量分（0–100，建议权重）

| 维度 | 分值 |
| --- | --- |
| 必填章节齐全 | 40 |
| 日志特征可解析 | 20 |
| 正则可编译 | 10 |
| 各章节信息量（≥20 字） | 10 |
| 图片完整 | 10 |
| 用户反馈权重（like/dislike） | 10 |

## 7. 接口设计

| 接口 | 用途 |
| --- | --- |
| `POST /knowledge/format/preview` | 不落库：`{content, doc_type}` → `{normalized_content, sections, profile_draft, issues, quality_score}`；前端「一键格式化」与「分屏预览」共用 |

| `GET /knowledge/{doc_id}/sections` | 返回文档分节（供预览/审核/定位） |

| 阶段 | 内容 |
| --- | --- |

## 11. 验收标准

1. case/playbook 入库后必定有标准章节与分节记录；缺必填章节无法存为 active。
2. 一键格式化对同一内容幂等，且不丢失正文信息。
3. 分屏「提交后视图」与保存后的实际格式一致（同一套规范化逻辑）。
4. 前端未点格式化直接保存，后端仍产出规范化内容与质量分。
5. 诊断剧本由模板解析自动生成；手填覆盖可生效且被标记 `manual_override`。
6. AI 回答可引用到「文档 · 章节 · 行号范围」。
7. 信息不足/意图模糊时先反问（含结构化选项），不硬答；用户补充后继续分析。

## 12. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 规范化误伤正文 | 规则幂等 + 改动对比预览 + 可撤销，不改动章节正文文字 |
| 人绕过前端直接调 API | 后端入库强制走 Normalizer + Validator |
| LLM 兜底产生错误结构 | 产物进 draft + 人工审核，不直接 active |
| 质量分被滥用 | 分值与阈值可配置，先用于提示与审核，不直接阻断 note/faq |
| 模型多表增加复杂度 | 新表均与文档 1:1/1:N，用 `create_all` 自动建表，开发阶段可重建库 |

## 13. 意图澄清与反问（新增）

用户描述往往宽泛/模糊，无法直接定位到细节。无论纯文本还是文本+附件，AI 都应在信息不足时**主动反问**，而不是硬答。

### 13.1 触发条件

| 场景 | 判断 |
| --- | --- |
| 缺少关键槽位 | 缺设备型号/城市/版本/现象/日志模块等（来自知识库 `features` 槽位） |
| 检索歧义 | 命中多条知识、或特征点不匹配导致无法唯一确定 |
| 前提冲突 | 用户描述与 `code_logic` / `knowledge` 冲突（低级误区） |
| 附件未定位 | 日志中未命中该问题的日志特征（定位不到） |

### 13.2 反问策略

- 优先**结构化选项**（从知识库 `features` 去重生成设备/城市/版本候选），而非开放式追问。
- 一次最多问 2–3 个关键槽位，避免连环追问。
- 说明为什么问（缺哪个槽位），并提供「直接回答 / 我来补充」入口。

### 13.3 两条路径

- **纯文本**：复用现有 `DiagnosticChatAgent` Stage 2.5 的 `analyze_and_ask_with_llm` / `check_and_generate_proactive_questions`，补充「槽位化反问」（从 profile.features 取候选）。
- **文本+附件**：`processFiles` → `run_analysis` 增加 `needs_clarification` 分支——分析前判断槽位；不足则返回反问（不跑 LLM 诊断）；用户补充后重新触发分析。

### 13.4 返回结构与前端

```json
{
  "needs_clarification": true,
  "questions": [
    {"slot": "device", "label": "设备型号", "options": ["D3C", "L13C"], "hint": "用于匹配同类案例"},
    {"slot": "city", "label": "现场城市", "options": ["潜江", "武汉"]}
  ],
  "reason": "缺少设备型号与现场信息，无法唯一匹配知识库案例"
}
```

- 前端以普通 assistant 气泡展示，问题可点选（选项按钮）；
- 用户补充后作为下一轮输入，保留会话上下文。

### 13.5 与强约束的关系

- **信息不足 → 反问（引导）**，不是「无支撑」结论；
- **信息充分但无 KB 证据 → 无支撑结论（不胡编）**；
- 反问不产生诊断结论。

### 13.6 验收

- 模糊问题（如"设备不上传视频"）→ 反问设备型号/城市/版本；补充后继续分析；
- 前提冲突（用户描述与代码逻辑不符）→ 先纠正再回答。
